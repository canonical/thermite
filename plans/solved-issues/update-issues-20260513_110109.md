## Findings (Ordered by Severity)

### 1. Critical: Failed command paths drop stdout, breaking error-driven logic
- Locations:
  - src/shell.rs:97-103
  - src/error.rs:13-17
- Details:
  - run_command returns ThermiteError::CommandFailed with stderr only.
  - stdout is discarded for non-zero exits, even though many Debian tooling commands emit actionable diagnostics to stdout.
- Impact:
  - Callers cannot make correct decisions from failed command output.
  - Debugging and retry loops lose important context.
- Recommended fix:
  - Extend ThermiteError::CommandFailed to carry both stdout and stderr.
  - Update all error-path parsers to consume combined output where appropriate.
- How fixed:
  - Added `stdout: String` field to `ThermiteError::CommandFailed` in `src/error.rs`.
  - Updated `run_command` in `src/shell.rs` to capture stdout and include it in `CommandFailed`.
  - Updated all `CommandFailed` construction sites in `src/steps/git.rs`, `src/steps/control.rs`, and `src/commands/update.rs` (find_changes_file) to supply `stdout: String::new()` where only stderr was previously available.
  - Updated all destructuring sites in `src/steps/lintian.rs` and `src/steps/patches.rs` to combine `stdout + stderr` for downstream parsers.
- Unit test:
  - `error::tests::command_failed_carries_stdout_and_stderr` — verifies `CommandFailed` carries both `stdout` and `stderr` fields.

### 2. Critical: Lintian parsing can produce false-clean results on non-zero exit
- Locations:
  - src/steps/lintian.rs:33-37
  - src/commands/update.rs:533-538
  - src/commands/update.rs:643-648
- Details:
  - run_lintian captures combined stdout+stderr only on success.
  - On CommandFailed, it parses stderr only.
  - If lintian prints diagnostics on stdout, errors/warnings can be undercounted or missed.
- Impact:
  - Workflow may continue despite unresolved lintian issues.
- Recommended fix:
  - After fixing finding #1, parse combined stdout+stderr for both success and failure paths.
  - Add regression tests with representative lintian failure output.
- How fixed:
  - `run_lintian` in `src/steps/lintian.rs` now destructures `CommandFailed { ref stdout, ref stderr, .. }` and parses `stdout.clone() + stderr` so the full output is available on non-zero exits.
  - This fix depends on Finding 1 (stdout added to `CommandFailed`).
- Unit tests:
  - `steps::lintian::tests::parse_lintian_output_classifies_errors_and_warnings` — verifies errors vs warnings are correctly split from representative lintian output.
  - `steps::lintian::tests::parse_lintian_output_from_combined_stdout_stderr` — verifies that the combined stdout+stderr path classifies tags correctly.

### 3. Critical: Patch refresh loop is incomplete on first failure path
- Locations:
  - src/commands/update.rs:446-480
  - src/steps/patches.rs:22-31
  - src/steps/patches.rs:39-51
- Details:
  - On PatchFailed, orchestrator only prompts the user.
  - quilt_push_all reports conflicted_files as empty.
  - Available helper quilt_push_force_merge is not invoked by the loop.
- Impact:
  - User can be prompted to resolve conflicts that were never force-materialized.
  - Flow diverges from the plan's intended quilt push -f --merge behavior.
- Recommended fix:
  - In run_interactive_patch_refresh, invoke quilt_push_force_merge when quilt_push_all fails.
  - Surface parsed conflicted files and then run quilt_refresh (or enforce explicit user confirmation after refresh).
- How fixed:
  - `run_interactive_patch_refresh` in `src/commands/update.rs` now calls `patches::quilt_push_force_merge(repo_dir).await?` immediately after `quilt_push_all` returns `PatchFailed`, materialising conflict markers in the working tree.
  - The conflicted file list from the force-merge result is used in the user-facing info box.
  - After the user resolves the conflict, a `prompt_yes_no` asks whether they refreshed or dropped; if refreshed, `patches::quilt_refresh(repo_dir).await?` is called before the loop iterates.
- Unit tests:
  - `steps::patches::tests::parse_failing_patch_name_extracts_last_patch` — verifies patch name extraction from quilt error output.
  - `steps::patches::tests::parse_conflicted_files_extracts_paths` — verifies conflict file paths are parsed from quilt output.
  - `steps::patches::tests::parse_failing_patch_name_empty_for_no_match` — verifies empty result when no match is found.

### 4. High: Interactive rebase is launched through a non-interactive command runner
- Locations:
  - src/commands/update.rs:255-262
  - src/shell.rs:36-40
- Details:
  - Workflow asks for interactive git rebase -i.
  - run_command pipes stdout/stderr instead of inheriting terminal streams.
- Impact:
  - Editor/TTY behavior for rebase -i may fail or be unreliable.
  - Phase 10 can block or fail unexpectedly in real runs.
- Recommended fix:
  - Add a dedicated run_interactive_command path that inherits stdin/stdout/stderr for interactive commands.
  - Use it for rebase -i and any future editor-driven workflows.
- How fixed:
  - Added `pub async fn run_interactive_command(program: &str, args: &[&str], cwd: &Path, env: &[(&str, &str)]) -> Result<()>` to `src/shell.rs`. This function uses `cmd.status().await` without piping any stdio, so the TTY is inherited.
  - Phase 10 in `src/commands/update.rs` now calls `crate::shell::run_interactive_command("git", &["rebase", "-i", ...], ...)` instead of `run_command`.
- Unit test:
  - `shell::tests::run_interactive_command_is_exported` — verifies the function is callable and returns an error (not a panic) for an unknown program.

### 5. High: .changes selection is nondeterministic and can upload stale artifacts
- Location: src/commands/update.rs:683-689
- Details:
  - find_changes_file selects the first .changes file returned from read_dir.
  - Parent directory can contain stale build outputs.
- Impact:
  - Wrong source package can be uploaded to PPA.
- Recommended fix:
  - Select by newest mtime and expected package/version prefix.
  - Prefer explicit .changes path emitted by the current build step.
- How fixed:
  - `find_changes_file` in `src/commands/update.rs` now collects all `.changes` entries, sorts them by modification time descending (`mt_b.cmp(&mt_a)`), and picks the first (newest) entry.
  - Falls back to name-order comparison if `mtime` is unavailable.
- Unit test:
  - `commands::update::tests::find_changes_file_returns_newest` — creates two `.changes` files with a 20 ms sleep between writes (ensuring different mtimes), then asserts the newer file is returned.

### 6. High: Vendor tarball selection is nondeterministic
- Location: src/steps/vendor.rs:68-74
- Details:
  - generate_vendor_tarball picks the first .orig-vendor.tar.xz found.
  - Multiple tarballs in parent directory are not disambiguated.
- Impact:

  - Both call sites in `src/commands/update.rs` (phases 8 and 9) were updated to pass `new_ver`.
- Unit test:
  - `steps::vendor::tests::vendor_tarball_expected_name_format` — asserts the constructed name is `"rustc-1.85_1.85.0+dfsg.orig-vendor.tar.xz"` for version 1.85.0.

### 8. High: autopkgtest-buildvm disk size argument is malformed
- Location: src/steps/autopkgtest.rs:57-64
- Details:
  - Disk option is passed as one arg with embedded space: "-s 100G".
  - The tool expects either two args (-s, 100G) or one arg without space (-s100G).
- Impact:
  - Testbed image creation can fail immediately.
- Recommended fix:
  - Pass as separate args: "-s", "100G".
- How fixed:
  - `build_testbed_image` in `src/steps/autopkgtest.rs` now constructs `let disk_size = format!("{disk_gb}G")` and passes `"-s"` and `&disk_size` as two separate entries in the args slice, replacing the previous single-token `format!("-s {disk_gb}G")`.
- Unit test:
  - `steps::autopkgtest::tests::disk_size_arg_contains_no_embedded_space` — demonstrates that the old single-arg form contained a space, and asserts neither of the two new args contains a space.
